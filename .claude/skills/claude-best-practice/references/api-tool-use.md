# Tool use, structured output and context in code

As of 2026-11-05. Beta names and platform support change, so check `tool-use-concepts.md` and `platform-availability.md` in the `claude-api` skill before shipping.

## Choosing the surface

1. Start simple. A single call fits classification, summarizing, extraction and Q and A. A workflow, where your code owns the steps, fits a known multi step pipeline. An agent, where the model chooses the steps, is for open ended work.
2. Build an agent only if all four hold: the task is multi step and hard to specify in advance, the outcome is worth the cost and latency, the model is capable at this kind of task, and errors can be caught and recovered (tests, review, rollback).
3. Four ways to run an agent. The harness is the loop and context handling. The deployment is where it runs.
   - Manual loop: you write the `stop_reason == "tool_use"` loop. You own everything.
   - Tool Runner (`client.beta.messages.tool_runner`): the SDK loops over tools you define. Harness only, you host. Default for a custom tool agent.
   - Managed Agents (beta): Anthropic runs the loop and hosts a per session sandbox. Harness and deployment. Claude API, Platform on AWS and Google Cloud (Anthropic managed).
   - Claude Agent SDK: the Claude Code harness as a library, with built in file, bash and search tools, hooks, subagents and sessions. Harness only, you host. A separate product from the Tool Runner.
4. Each Tool Runner iteration yields the assistant message before tools run, so you can gate or approve in the tool function, override the pending request, intercept errors, change results (for example add `cache_control`), bound the loop with `max_iterations`, stream, and compact. "I need control" is rarely a reason for a manual loop. Use a manual loop only to own the whole loop: a custom transport, request shapes the SDK cannot build, avoiding the beta dependency, or interleaving other work mid loop. In current SDKs the runner uses a message thread by default (rule 38).
5. A manual loop runs until `stop_reason == "end_turn"`, always appends the full `response.content`, and matches every `tool_result` to its `tool_use_id`.
6. Managed Agents suits a stateful agent with a workspace, persisted versioned configs, long sessions, scheduled runs and a deliverable that must meet a rubric. Create the agent once, store its id, and start sessions from it. Never create agents in the request path. Permission policies and vaults are in `agent-orchestration.md`.
7. Validate inputs and gate destructive operations behind human approval, in the runner and in a manual loop.

## Designing the tool surface

8. Bash gives breadth but the harness sees an opaque string. A dedicated tool has typed arguments you can intercept, gate, render or audit. Start with bash and promote an action to its own tool when it needs gating on a security boundary (reversibility is the test: `send_email` is gateable, `bash -c "curl -X POST"` is not), a staleness check (an `edit` tool that rejects a write if the file changed), custom rendering, or scheduling (read only tools can run in parallel, bash cannot be told apart from `git push`).
9. Descriptions: be prescriptive about when to call. Recent Opus models reach for tools more conservatively and trigger conditions in the description measurably raise the call rate. Describe every property, use `enum` for fixed sets, mark only truly required parameters as required. At least 3 to 4 sentences per tool. Specific names (`get_current_weather`, not `weather`), namespaced where there are many (`github_list_prs`). What a tool returns is in `tools-mcp.md`.
10. Consolidate related operations into one tool with an `action` parameter. Return only high signal fields with stable identifiers, because bloated results waste context.
11. `input_examples` on a tool (1 to 5) must validate against its schema (else 400) and cost about 20 to 50 tokens each for simple ones and 100 to 200 for complex ones. They are the fix for wrong parameters on a complex schema. Not supported on server tools or toolsets.
12. Steer triggering from the system prompt as behaviour ("investigate with the tools before responding") without naming a tool. A preference for one tool belongs in that tool's description (`prompt-structure.md`). A tool use system prompt of a few hundred tokens is added automatically.

## Results and calls

13. On failure return a `tool_result` with `is_error: true` and an informative message. The model usually acknowledges it and tries another way. Never drop a failed result.
14. Parallel calls are on by default. Run them concurrently and return all `tool_result` blocks in one user message with no text before them. Splitting them across messages trains the model to stop calling in parallel. `disable_parallel_tool_use: true` allows at most one call.
15. Mid turn user input goes as a text block after the last `tool_result` in that user message. User text inside a `tool_result`, or in a system message right after a tool result, is treated as prompt injection on Sonnet 5.5 and Haiku 5.5 (`prompt-structure.md` rule 12).
16. Strict tool use: `strict: true` as a top level field on the tool, with `additionalProperties: false` and `required`. It guarantees the input validates. It is not compatible with programmatic tool calling, and not available on Fable models in a CMEK organization.
17. Eager input streaming: on a streamed request with your own tools, set `eager_input_streaming: true` on each tool, so large inputs stream instead of arriving after a long silent buffer. It removes server side validation, so the client must:
    1. Validate the parsed input against the schema before running the tool. Typed helpers do this (TypeScript `betaZodTool`, Python typed `@beta_tool`, Java annotated classes, Go struct tags, Ruby `BaseTool`). TypeScript `betaTool()` and PHP `BetaRunnableTool` do not, so validate in `run`.
    2. Check `stop_reason == "max_tokens"` when a `tool_use` is present, since a truncated input often parses as a valid partial object. Retry with a higher `max_tokens`. Stop on `refusal` and never run that turn's tools.
    3. Catch only the SDK's JSON error, rethrow typed API errors, and cap retries.
    4. On a validation failure with the block in hand, return an `is_error` result carrying the raw input. If the SDK raised before the block completed there is no `tool_use_id`, so re issue the request.
    Leave it off for non streaming requests, server tools, and through a proxy or older Bedrock deployment that rejects the field. The old `fine-grained-tool-streaming-2025-05-14` header is cruft and returns 400 beside a computer or browser toolset.
18. `pause_turn`: the server side loop caps at 10 iterations. Resume by re sending the user message and the assistant `response.content`. Do not add a "Continue." message. Cap continuations (for example 5). The Python and TypeScript tool runners resume it themselves from `anthropic` 1.1.0 and `@anthropic-ai/sdk` 0.121.0, each resume counting toward `max_iterations`; older releases end the runner on a paused turn. On a thread, resume with a continue request and `messages: []`.
19. Never match on the serialized tool input. Parse it with a JSON parser, because escaping differs between models.

## Server and client tools

20. Server tools (code execution, web search, web fetch) run on Anthropic's side. Declare them and results arrive as blocks in the same response. Use the latest type your model supports: `web_search_20260209`, `web_fetch_20260318`, `code_execution_20260521`. The web tools do dynamic filtering with code execution inside, so do not also declare `code_execution`. Web fetch only fetches URLs already in the conversation. The Models API reports server tool support (`capabilities.server_tools`). Server tools also run inside a Batches request.
21. Code execution has no internet, about 5 GiB of RAM and disk, and containers that persist 30 days and can be reused by `container_id`. Sanitize any downloaded filename with `basename`.
22. Client tools (bash, text editor, memory, computer use) you execute. Bash and the text editor are schema less: declare the type and name, send no `input_schema`, and never define your own tool named `bash`. Anthropic hosts no sandbox for client tools: the isolation is yours.
23. Bash safety: treat every command as untrusted. Isolated environment, an allowlist of executables, reject shell operators, timeouts and resource limits, log every command. A blocklist is not enough.
24. Text editor safety: canonicalize the path and confine it to a project root, reject `..`, symlinks and encoded traversal, require `str_replace` to match exactly one occurrence.
25. Computer use goes through `computer_toolset_20260801` (no `name`, no beta header, echo `toolset_name: "computer"` in results). On the Claude API and Google Cloud, Opus 5.5, Sonnet 5.5 and Haiku 5.5 accept only the toolset; Bedrock still accepts the older `computer_20251124` (beta `computer-use-2025-11-24`). The two forms cannot share a request. `computer_20250124` is rejected everywhere on these models.
26. MCP connector (beta `mcp-client-2025-11-20`) needs both halves: `mcp_servers` and a matching `mcp_toolset` entry. Either alone is a validation error.
27. Advisor tool (beta `advisor-tool-2026-03-01`, Claude API and Platform on AWS): `{"type": "advisor_20260301", "name": "advisor", "model": ...}`. The advisor must be at least as capable as the executor or it is a 400. Sonnet 5.5 as executor rejects Opus 4.8, 4.7, 4.6, Sonnet 5 and Sonnet 4.6 as advisors. Switch on the result's content type: `advisor_result` has plaintext, `advisor_redacted_result` has `encrypted_content` you can only replay, `advisor_tool_result_error` has an `error_code`. Append the full `response.content` including advisor blocks on later turns. Removing the tool while history holds advisor results is a 400.

## Scaling tools and context

28. Programmatic tool calling lets the model write a script in the code execution container that calls your tools, so intermediate results never enter its context and only the final output returns. Use it for many sequential calls or large intermediate results. Declare `code_execution_20260120` and set `allowed_callers` on your tool. The reply to a pending call contains only `tool_result` blocks. Not on Bedrock or Vertex.
29. Tool search with `defer_loading: true` suits many tools with few relevant per request: past about 10 tools or 10K tokens of schemas. Keep the 3 to 5 most used tools non deferred. Discovered schemas are appended, so the cache survives. Never defer every tool, never defer the search tool itself, and a deferred tool cannot carry `cache_control` (400).
30. Tool search is for discovery (the model decides). Mid conversation tool changes are for control (your app decides): the tool must already be declared with `defer_loading: true`, a removal sits right before an assistant message or last, and to change a definition send a removal first (beta `mid-conversation-tool-changes-2026-07-01`; a definition inside a mid conversation message is beta `inline-tools-2026-09-15`). Not on Sonnet 5 or Foundry.
31. Agent Skills through the Messages API: `container={"skills": [...]}` plus the code execution tool and beta `code-execution-2025-08-25`. This is not Managed Agents.
32. Three tools for a long context, and many long running agents use all three. Context editing clears stale tool results or thinking blocks by rule (beta `context-management-2025-06-27`, strategies `clear_tool_uses_20250919` and `clear_thinking_20251015`); it is a window tool, not a saving, because each pass rewrites the cached conversation. Compaction summarizes older turns on the server (rules 33 and 34). Memory persists across sessions (rule 35).
33. Compaction on demand (beta `compact-2026-09-04`, the top level `compaction: {type: "summarize"}` parameter) is the default form wherever it is available (Claude API, Platform on AWS, Google Cloud, Foundry; not Bedrock). Your code decides when: after a turn, add the last response's `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and `output_tokens`, compare with a limit you set below the context window, and compact before you outgrow it. Send the conversation with the same `system` and `tools`; the reply is one `compaction` block with `stop_reason: "compaction"` and no reply. Put the block first in `messages`, drop the messages it summarizes, and send it unchanged with the beta header on every later request. Check `stop_reason` before looking for the block: `max_tokens` (raise it), `tool_use` (tell the summarizer not to call tools), `refusal` or `end_turn` (continue without a summary). A custom `instructions` string replaces the default prompt entirely, so say what the summary must retain. Images, documents, uploads and fetched URLs inside the summarized range are gone; restate or re upload what a later turn needs. Mid conversation system messages and per message effort inside the range stop applying; state them again after the block. Do not send `task_budget.remaining` with the block. `compaction` and `context_management` cannot share a request. Kept turns keep their thinking on preserved thinking models, which is what makes keep recent turns and background compaction safe.
34. Threshold compaction (beta `compact-2026-01-12`, `context_management.edits: [{type: "compact_20260112"}]`) lets the API compact inside an ordinary request when input tokens reach `trigger.value` (default 150,000, minimum 50,000). Append the full `response.content`, never just the text, or the state is lost. `pause_after_compaction: true` returns the block alone with `stop_reason: "compaction"`, which is how to enforce a total token budget. Thinking from before the block is not carried forward, and any turn you reinsert after it must have its thinking stripped or `drop_block` set. On Bedrock this is the only server side form.
35. The memory tool is client side over a `/memories` directory with `view`, `create`, `str_replace`, `insert`, `delete`, `rename`. Never store secrets, take care with personal data, and use a directory per user in a multi user system.
36. Citations: `citations: {enabled: true}` on every document block, or none. Incompatible with `output_config.format`.
37. Documents and images: put a PDF before the text block. Use the Files API (`file_id`) for the same file across requests, and match the block type to the file's type.

## Message threads

38. A thread (beta `message-threads-2026-08-12`, on every request) keeps the conversation on the server for a short time, so each later request sends only the new messages. Use it in long tool loops and long chats: smaller requests and lower, steadier time to first token as the conversation grows. It changes neither price nor rate limits and caches nothing by itself: keep `cache_control` on every request. Claude API, Platform on AWS, Google Cloud (Anthropic managed) and Foundry; not Bedrock or Vertex.
39. Create with the full `messages`, `system` and `tools` plus `thread: {type: "create"}`; continue with only the new messages and `thread: {type: "continue", previous_message_id}` from the latest response id. `system` and `tools` are create only (sending them on a continue is a 400). `model`, `thinking`, `output_config`, `tool_choice`, `context_management`, top level `cache_control` and the beta set are fixed per thread (`thread_fingerprint_mismatch`). To change any of them start a new thread with the full conversation.
40. The application stays the source of truth. A thread is best effort: it expires 5 minutes after its last request and is deleted within an hour. On 404 `thread_not_found` replay the full conversation from your own copy in a new create request. Build the replay path from day one, and never send a message the thread already has. Prefer the SDK thread helper, which creates, continues, keeps the copy and replays once. Threads are not ZDR eligible.
41. A thread is append only. To compact, start a new thread from a summary you write; `compaction` and `context_management` are rejected on a thread (except `clear_thinking_20251015` with `keep: "all"`). Threads also do not support Batches or token counting. Send `fallbacks` on every request of a thread or on none. After a `stop_reason: "refusal"`, do not continue the thread. On a model with preserved thinking, a new thread with changed `system` or `tools` must leave the earlier thinking blocks out.
42. At most 4 `cache_control` breakpoints: the top level one counts, and the create request's `system` and `tools` breakpoints count again on every continue.

## Structured outputs

43. Two features: JSON outputs with `output_config.format` (`json_schema`), and strict tool use. Prefer `client.messages.parse()` where the SDK has it, which validates against your schema. The old `output_format` is deprecated.
44. Supported schema: object, array, string, integer, number, boolean, null, `enum`, `const`, `anyOf`, `allOf`, `$ref`, common string formats, and `additionalProperties: false` which is required on every object. Not supported: recursive schemas, `minimum`, `maximum`, `multipleOf`, `minLength`, `maxLength`, complex array constraints, external `$ref`, lookaround in regex. `minItems` is 0 or 1 only. The Python and TypeScript SDKs strip unsupported constraints and validate them on the client.
45. Required properties are output first. If order matters mark all of them required. Compare enum values case insensitively.
46. A schema field asking for reasoning can trigger a `reasoning_extraction` refusal. A refusal can return output that does not match the schema, and `max_tokens` can leave it incomplete, so check `stop_reason` first.
47. The first request with a new schema is slower while the grammar compiles. It is cached 24 hours. Changing only `name` or `description` does not invalidate that. Changing the format does invalidate the prompt cache.
48. Per request limits across strict schemas: 20 strict tools, 24 optional parameters, 16 `anyOf` or type array parameters. Combining strict tools with JSON output can make the model answer with a tool call instead of JSON. On Haiku 5.5 with thinking off, a JSON format beside client tools can make the model skip a needed tool call; keep thinking on there.
49. Use `output_config.format` for judge calls, not "respond with only JSON", which breaks on unescaped quotes.

## Checklist

- [ ] Surface chosen on the four agent criteria, Tool Runner unless there is a stated reason
- [ ] Tool descriptions say when to call, every property described
- [ ] Failed tools return `is_error`, parallel results in one message with no text before them
- [ ] Eager streaming paired with client side validation and `max_tokens` check
- [ ] `pause_turn` resumed with a cap
- [ ] Bash and file tools confined and logged
- [ ] Long loops: on demand compaction with an app chosen trigger, and a thread where the platform has them, with the replay path tested
- [ ] Structured output schema within the supported subset
